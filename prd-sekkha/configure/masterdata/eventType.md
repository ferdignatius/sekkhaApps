# PRD: Master Data - Event Type

| Metadata | Detail |
| --- | --- |
| **Document** | Product Requirement Document (PRD) |
| **Feature** | Master Data Event Type |
| **Application** | Sekkha Apps - Configure Module |
| **Version** | 2.0.0 |
| **Status** | Approved / Ready for Development |

## 1. Description

Event Type classifies activities. It appears when creating events and supports event filtering. Each Event Type defines default points automatically applied to new events. Admin can change this default at any time.

Event Type management is internal configuration. `member` and `activist` cannot access it.

## 2. Roles and permissions

| Action | `admin` | `organizer` | `activist` | `member` |
| --- | :---: | :---: | :---: | :---: |
| View list and detail | Yes | Yes | No | No |
| Create | Yes | No | No | No |
| Update | Yes | No | No | No |
| Activate or deactivate | Yes | No | No | No |
| Delete | Yes | No | No | No |

`organizer` may read Event Types to select one while creating an event. Only `admin` changes master data. API must use these English role values exactly.

## 3. Default data

| Code | Name | Color | Description | Default points |
| --- | --- | --- | --- | ---: |
| `regular-service` | Regular Service | `#4262FF` | Regular or special temple service | 50 |

Admin may create Event Types such as retreat, meditation, social activity, meeting, or training. Default points are configurable per Event Type.

When an organizer selects an Event Type during event creation:

1. `default_point_reward` autofills the event point value.
2. The organizer may override points for that event if authorized by event rules.
3. Existing events retain their saved point value when Event Type default changes.
4. New events use latest Event Type default.

## 4. Data model

| Field | Type | Required | Rules |
| --- | --- | :---: | --- |
| `id` | `cuid` | Yes | Generated by server |
| `code` | string | Yes | Unique, lowercase kebab-case, 2-50 chars |
| `name` | string | Yes | 2-50 chars |
| `color` | string | Yes | Hex `#RRGGBB` |
| `description` | string | No | Maximum 500 chars |
| `default_point_reward` | integer | Yes | 0-10000, default 0 |
| `is_active` | boolean | Yes | Default `true` |
| `created_at` | DateTime | Yes | Server generated |
| `updated_at` | DateTime | Yes | Server generated |

## 5. Validation and business rules

1. Validate every field on the API boundary.
2. `code` must be unique and immutable after creation.
3. `name` must be trimmed before storage.
4. `color` must match `^#[0-9A-Fa-f]{6}$`.
5. `default_point_reward` must be an integer between 0 and 10000.
6. Inactive Event Types do not appear in new-event selection lists.
7. Existing events remain linked to inactive Event Types.
8. Do not hard-delete an Event Type referenced by an event. Return `409` or use deactivation.
9. Changes to default points affect new events only, never historical events or point transactions.
10. Mutations require `admin`; reads require `organizer` or `admin`.

## 6. UI requirements

- **Route**: `/configure/master/event-type`
- Table columns: Code, Name, Color, Description, Default Points, Status, Updated At, Actions.
- Admin sees create, edit, activate, deactivate, and delete actions.
- Organizer sees read-only list.
- Create/edit form includes code, name, description, default points, active status, and color picker.
- Show live color swatch and point preview.
- Disable delete when referenced; explain that deactivation is required.
- Use pagination or server-side filtering when list grows.
- Minimum touch target: 44px.
- Expose validation errors with labels and accessible status announcements.

## 7. API contract

Base route uses `/api/configure`. No `/v1` prefix.

Every response uses this envelope:

```json
{
  "status": "success",
  "code": 200,
  "message": "Request completed successfully",
  "data": {}
}
```

`status` is `success` or `fail`. `code` equals HTTP status. `message` is always a string. `data` contains payload or `null` on failure.

## 8. Acceptance criteria

| ID | Scenario | Expected result |
| --- | --- | --- |
| AC-01 | Admin creates Event Type with valid default points | Data persists and appears in new-event selection. |
| AC-02 | Admin updates default points | Future events use new value; existing events do not change. |
| AC-03 | Admin deactivates used Event Type | New-event selection hides it; existing events remain valid. |
| AC-04 | Admin attempts delete of used Event Type | API returns `409` envelope; data remains intact. |
| AC-05 | Organizer reads Event Types | API returns active and permitted data in `data`. |
| AC-06 | `member` or `activist` reads Event Types | API returns `403` envelope. |
| AC-07 | Invalid color or points submitted | API returns `400` envelope; no partial write. |
| AC-08 | Any response is returned | Contains `status`, `code`, `message`, and `data`. |
